# Launch assets: token pictures, descriptions and links

The Launch page lets a creator add a picture, a short description and website / X / Telegram links to a token. They are stored in one **public Cloudflare R2 bucket**. Setting it up (bucket, API token, custom domain, CORS, Vercel variables) is in [R2_LAUNCH_ASSETS.md](R2_LAUNCH_ASSETS.md). Until it is set up the Launch page says **"Image upload is not set up yet"** and every other part of the page works. Creating a token without a picture, description or links never needs the bucket.

(Earlier versions used a Supabase Storage bucket. That path is gone; only the address of old files is still understood when reading, see below.)

## How it works

- **Route.** No separate function file: `api/swings-data.ts` has two `route=` values, rewritten in `vercel.json`: `/api/swings-upload` (POST) and `/api/swings-meta` (GET). The code is in `api/_swingsUpload.ts`; the rules (types, sizes, names, the details file) are in `src/swings/launchmeta/core.ts`; the signer is `src/swings/launchmeta/r2sign.ts`.
- **Sign-in.** `sign` needs the wallet sign-in session the rest of the site uses (one plain message signed once; no transaction, no key). It is checked against the site database (`SUPABASE_URL`). Without a session the answer is 401.
- **What may be uploaded.** A JPG, PNG or GIF up to 10 MB, or a details JSON up to 4 KB. The server refuses anything else before signing a link, the link itself is bound to that file type and size, and the page also reads the picture's first bytes so a renamed file is refused.
- **Limits.** 12 upload links per wallet per hour, 40 per IP per hour, plus the general per-IP limit. These counters are in memory per server instance (see `docs/operations-2026-10-security.md`).
- **Names.** A picture is stored at `img/<sha256 of its bytes>.<png|jpg|gif>` and a Solana token's details file at `meta/<sha256 of its bytes>.json`; the server does not issue a link for a name that already exists. The hash is computed by the browser and trusted only as a name: the server never sees the bytes.
- **Link lifetime.** A presigned link is valid for five minutes and for one path only.
- **Solana.** The details file (name, symbol, description, `image`, `extensions.website/twitter/telegram`) is uploaded when the creator presses Review, before anything is signed. Its address becomes the token's on-chain metadata `uri` (200 characters at most). A creator can still use their own link instead (Advanced options), but not both.
- **Ethereum-style networks (BNB Chain, Ethereum, Polygon).** The token contract has no uri, so the picture and details are published **after** the token exists, to `evm/<chain>/<token address>.json`. The server accepts that only from the wallet that created the token: the caller sends the creation transaction hash, and the server reads the receipt from a node and requires Aretia's factory's `TokenCreated` log naming that token and that wallet.
- **Showing it.** `/api/swings-meta?chain=...&address=a,b` returns the picture, description and links for up to 20 tokens (cached ~2 minutes). For Solana the server reads the token's metadata `uri` from the chain and follows it only if it points into the bucket under `meta/`; for Ethereum-style tokens it reads `evm/<chain>/<address>.json`. A token made before the move has an old Supabase address on the chain; if its file was copied to R2 (optional Step 7 of the guide) the address is mapped to the same path on R2. The token page and Launch Box show the result, read again with the same strict rules; links open with `noopener noreferrer nofollow` and text is always shown as text.
