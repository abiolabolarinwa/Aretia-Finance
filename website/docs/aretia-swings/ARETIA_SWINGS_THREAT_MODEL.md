# ARETIA SWINGS: THREAT MODEL (direct-integration engine)

This covers the Aretia-owned engine (`src/swings/engine`, `dex`, `execution`). The aggregator-client threats are in `docs/audit/threat-model.md`. "Status" is what exists in code with tests today.

When Aretia routes and builds transactions itself, the correctness burden moves to Aretia: a wrong address, wrong maths or wrong calldata can lose user funds with no aggregator to blame or to catch it.

| # | Threat | Where | Defence today | Status / gap |
|---|---|---|---|---|
| E1 | Wrong or spoofed router/factory address in the registry | `dex/entries.ts` | Entries are real deployments; `npm run test:live` proves each contract exists, the factory finds a real pair, and the router accepts Aretia's calldata. Addresses are lower-case constants in code, not fetched at runtime | Mitigated for four V2 venues. A new venue must pass the same live test before use. Does not protect against an upgradeable router being replaced later (re-run the live test periodically) |
| E2 | Malicious or fake pool (honeypot token, rigged reserves, pair that is not from the real factory) | `dex/evmV2.ts` | Pools are found only through the venue's own factory `getPair`; the pair must contain exactly the requested tokens; empty reserves mean inactive | Partial. A real factory can still hold a pair for a malicious token: that is a token-risk question (risk engine), not a pool-authenticity one |
| E3 | Price manipulation (flash-loan skew of a pool just before quoting) | `engine/*`, `dex/directEvm.ts`, `solana/directSolana.ts` | Every built swap carries a mandatory non-zero `minOut`; at build time the venue itself is asked what it would pay now (router `getAmountsOut`, V3 quoter, or a program simulation) and the swap is blocked if that is below the minimum; the exact transaction is then simulated. A manipulated pool therefore cannot fill below the user's floor | Mitigated for the user's own floor. Aretia does not yet compare a pool's price against other pools to warn about an outlier |
| E4 | Stale liquidity | `liquidity.ts`, `routing.ts` | Every pool carries `updatedAt` and block; pools older than five minutes are ignored, older than 30 s are penalised, an older read never overwrites a newer one | Mitigated for what is in the store. Nothing refreshes the store automatically yet (no indexer) |
| E5 | Transaction substitution (the transaction signed differs from the one quoted) | `execution/evmV2Builder.ts`, `dex/evmV3.ts`, `solana/builder.ts` | EVM calldata (V2 and V3) can be decoded back to its parts and round-trips under property tests; Solana transactions carry a plain-language step list built alongside the instructions and are judged by their effect on the wallet; the Solana wallet-returned message is compared to the built one | Partial. The UI shows the Solana step list as notes but not the decoded EVM calldata |
| E6 | Simulation mismatch (simulated but not what is sent) | `simulateV2Swap` | Simulation runs the exact `to`/`data`/`value` that will be sent | Mitigated at the builder; the final send path must reuse the same plan object (to be enforced when wired) |
| E7 | Router exploit or approval abuse | approvals | Approval is exact-amount, to the router only (`EvmTxPlan.approval`) | Mitigated in design. Not yet wired into the direct path's execution |
| E8 | Slippage / sandwich | all swaps | Mandatory non-zero `minOut`; the user chooses slippage. No private transaction submission | Not mitigated beyond slippage |
| E9 | Fee-on-transfer and rebasing tokens break exact-amount maths | `evmV2Builder.ts` | `feeOnTransfer` variants exist; the standard path assumes ordinary tokens | Partial: nothing detects a taxed token automatically in the direct path (the risk engine's tax signal is the guard) |
| E10 | Route reasoning is opaque | `routing.ts` | Fixed scoring formula; every adjustment is written to `reasons`; determinism is tested | Mitigated |
| E11 | Provider degradation unnoticed | `engine/health.ts`, `registry.ts` | Health windows, `ACTIVE/DEGRADED/DISABLED`, cooldown and recovery; the engine skips disabled and penalises degraded venues | Mitigated in logic. Nothing records real adapter calls into health yet in production wiring |
| E12 | Split-order assumptions break at execution | `solana/directSolana.ts`, `dex/evmV3.ts`, `dex/directEvm.ts` | Splits now execute atomically: Solana puts every swap in ONE transaction, each leg with its own on-chain floor taken from that leg's own pricing; EVM splits Uniswap V3 fee tiers of one pair inside ONE router `multicall`, each leg with its own `amountOutMinimum`. A split is only offered when the price impact is at least 30 bps and the split beats the best single pool by at least 10 bps. The venue price of every leg is re-read at build time and the exact transaction is simulated, with the EVM simulation summing every leg | Mitigated for these two shapes (live: 10,000 ETH to USDC split on Uniswap V3, router accepted both legs and paid exactly the quote). Splits across different routers (V2 style) need a contract and are not offered. The Solana split path is proven by unit tests, not by a mainnet case (mainnet pools were too deep to trigger it) |
| E13 | Reorgs, duplicate events, malformed data | `indexer/evmIndexer.ts`, `indexer/solanaIndexer.ts` | EVM: only blocks `confirmations` deep are read (12 Ethereum, 15 BNB, 64 Polygon, 10 Base); removed or malformed logs are skipped; a node that refuses a large range is retried with halves. Solana: only `finalized` transactions are read, failed ones are ignored, the instruction must belong to the expected program and match its discriminator, data length and account layout, and the cursor holds the newest signature per account. Re-reading is idempotent on both. A busy account that returns a full page after the cursor is reported as `truncated`, not hidden | Mitigated for the EVM factory feed and for Solana Raydium CPMM and Orca. **Meteora DAMM v2 pools are not indexed** (no account only creation touches). Confirmation depths are judgement, not proof |
| E14 | Address poisoning / spoofed token symbols | tokens | Identity is `chain:address`, checksum verified, collisions flagged | Mitigated |
| E15 | Buyback misallocation | `core/fee.ts`, `solana/directSolana.ts`, `router/router.ts` | The Solana executor puts the buyback swap in the SAME transaction as the user's swap, with its own on-chain floor, delivered to the one configured address; the simulation must show the ACT arriving there or the swap is blocked. It is off by default and fails closed: missing treasury or executor address means `config-missing`, aggregator routes are dropped while it is on, a swap that sells ACT is not offered, no ACT route means no swap. The user's amount is never reduced; the buyback is on top and shown separately | Built, tested (unit and one live simulation with a test configuration), **never enabled**. Needs the owner's reviewed configuration. EVM: not built |
| E16 | A venue program changes (fee logic, account list) and Aretia's builder goes stale | `solana/meteoraDamm.ts`, `solana/raydiumCpmm.ts`, `dex/evmV3.ts` | Prices for DAMM v2 and V3 come from the venue itself (simulation / quoter), so a fee change cannot make quotes drift; every build is simulated on the real program, so a changed account list fails safe before signing | Mitigated. Raydium CPMM uses local maths: its pools are re-read at build and checked against the quote |
| E17 | Token-2022 transfer fees make outputs smaller than a venue's headline number | ACT and other Token-2022 mints | DAMM quotes are the delivered, post-fee amount; CPMM pools with Token-2022 mints are excluded | Mitigated for what is routed. Aggregator claims are not adjusted (they are non-core and are re-simulated at build) |

| E18 | A multi-hop route's second swap fails or is starved after the first succeeds | `solana/directSolana.ts` | Both hops are in ONE transaction, so a failure undoes both. The second hop sells 10 bps less than the first is expected to deliver, hop 1's on-chain floor equals what hop 2 sells, and the whole transaction is simulated on the real programs before signing | Mitigated. A very small amount of the intermediate token can remain in the wallet |
| E19 | Database migration changes unexpectedly or runs twice | `db/migrate.ts`, `scripts/apply-migrations.ts` | Numbered files, each in its own transaction, checksum recorded, an edited-after-applied file refused, one runner at a time (advisory lock), dry run, the connection string never printed. Tested on a real Postgres engine including row level security | Tested on PGlite, **not run against Aretia's Supabase project** |

| E20 | Protected sending used to relay arbitrary traffic or move other funds, or silently not protecting | `solana/jito.ts`, `api/_swingsSubmit.ts`, `scripts/walletSwap.ts` | The relay forwards only a transaction that is signed, within the Solana size limit, carries a tip to one of Jito's published tip accounts paid by the signer and between 1,000 and 1,000,000 lamports; it keeps nothing, is off by default, origin-allow-listed and rate limited. In the page, while protection is on only Aretia routes (which can carry the tip) are offered, and if the private send fails nothing is sent the public way | Tested (unit, relay tests, one live tipped simulation). The signed transaction passes through Aretia's server; it cannot be altered without breaking the signature. Protection lowers the chance of a sandwich; it is not a guarantee |
| E21 | The public quote API used to hammer RPCs or mislead integrators | `api/_swingsQuote.ts` | Off by default, per-caller rate limit, strict input checks, own routing only (no aggregator), EVM chains follow the operator list, errors do not leak internals, nothing is signed or sent | Mitigated for a first version. It trusts the integrator to show the user the simulation result and to sign only what it returns |
| E22 | Staged rollout bypassed | `runtime.ts`, `api/_swingsStatus.ts` | Only hashes of allowed wallets reach the page, and review and signing check them | A brake on a non-custodial page, **not access control**: someone who edits the page code can skip it. It limits accidents and early exposure, not an attacker |
| E23 | A venue's account list changes (PumpSwap added three trailing accounts the published IDL did not list) | `solana/pumpswap.ts`, `solana/meteoraDlmm.ts` | Every build is simulated on the real program before signing, so a changed list fails safe and the route is simply not offered; the accounts were found from real transactions, not only the IDL | Mitigated. Coverage can drop without warning when a program changes; the shadow data and the live suite show it |

## What is not covered at all
Raydium AMM v4 and CLMM, Manifest, proprietary AMMs, Uniswap V4 and other EVM venues with different interfaces, Meteora DAMM v2 indexing, EVM buyback, private EVM submission, cross-chain, and any signed real swap.
